# REQUIREMENTS

Stage 0: the problem statement and the requirements. Written 2026-10-24. Every item points to the decision that fixes it; items without a decision are marked Proposed.

## 1. Problem statement

Given an image, a video (with its audio) or a standalone audio clip, estimate the probability that the content is fake (synthetic or manipulated), and say which modality carries that evidence. Fake means one of: a face in an image or video that was swapped, re-enacted or driven by audio; an image generated by a GAN or diffusion model; speech that was synthesised or converted; audio and video that were manipulated separately. The system is built from zero in this repository (D-001) as a documented path: a simple MVP first, then at least 7 iterations that each follow from a written hypothesis and end in a measured result (D-004). The aim is a result comparable with published detectors on a protocol defined and run here, not the best model (D-005).

## 2. Inputs and outputs (D-002, D-011, D-018, D-019)

| Input | What the system returns |
|---|---|
| A still image: a face-manipulated image (including a frame from face-swap or lip-sync video) or a fully generated image | One visual score, which is also the fused score |
| A standalone audio file | One audio score, which is also the fused score |
| A video with audio | A visual score, an audio score and a fused score; each is a probability of fake in [0, 1] |

No temporal localisation in the first version (D-011). The scores are calibrated by temperature scaling (D-024).

| ID | Requirement |

## 5. Evaluation requirements (D-012, D-024; details in PROTOCOL.md)

| ID | Requirement |
|---|---|
| E1 | No person, source video or recording appears on both sides of any split; a script proves it |
| E2 | The headline is ROC-AUC on datasets never used in training, with a 95 percent bootstrap interval; in-dataset numbers are reported and never the headline |
| E3 | At least 3 seeds per candidate; mean, standard deviation and a paired bootstrap interval; if intervals overlap, the simpler or cheaper candidate is preferred and this is stated |
| E4 | The decision threshold and the temperature are chosen on validation data only |
| E5 | The final test split is touched once per frozen iteration, enforced by the `--final` guard and a ledger |
| E6 | The cost axes (parameters, FLOPs, peak VRAM, seconds per epoch, epochs to a validation target, learning-rate sensitivity, ease of fine-tuning) are measured for every candidate |

## 6. Constraints

- Hardware: one RTX 5070 with 12 GB (about 11 GiB usable), 24 CPU threads, 31 GB RAM, 404 GB on drive D: (ENV-DESKTOP-GPU, D-007).
- Time: seven calendar days to 2026-10-30 (D-009, D-016).
- Claims discipline: no "real-time", "state of the art" or "better than X" without a head-to-head run on the same protocol (CLAUDE.md rule 8).
- Data terms: Celeb-DF and FakeAVCeleb forbid publishing derived data (D-020), which limits the figures in the paper.

## 7. Deliverables (D-003, D-014)

The software, an IEEE-format paper (LaTeX), a technical report and a presentation, built continuously from the logs.

## 8. Success criteria

Each criterion is checkable from the repository. None states an expected result.

| ID | Criterion |
|---|---|
| S1 | The evaluation protocol is frozen and its acceptance test A1 to A8 (PROTOCOL.md) passes before any model result is produced |
| S2 | The MVP is evaluated end to end for each modality path with at least 3 seeds under the frozen protocol |
| S3 | At least 7 iterations after the MVP, each with a hypothesis, success and failure criteria written before the run, a measured result and a decision, failures included |
| S4 | A comparison table of the candidate models with accuracy, the cost axes and intervals, from which the final choice is justified |
| S5 | A headline cross-dataset ROC-AUC with intervals for each modality path, reported next to the in-dataset numbers and next to the baseline of S6 |
| S6 | "Comparable with published detectors" is met as defined below |
| S7 | The rPPG feasibility test is run with its thresholds written beforehand and ends in an adopt or do-not-adopt decision (D-006) |
| S8 | The paper, report and slides contain only numbers that trace to a logged experiment |

### Definition of "comparable with published detectors" (Decided, D-025 as amended 2026-10-24: non-inferiority, see DECISIONS.md)

A published detector family is re-run under our protocol (for example a plain Xception on FF++ c23 tested on other datasets, the usual protocol of R-017) with the same data, split, budget and metric as our system, and both results are reported with intervals. Our result is called comparable to the baseline when the interval of their paired difference contains zero or favours the baseline by less than a margin stated before the run. Numbers quoted from papers are shown only as context with their own protocol named (RESEARCH.md rule), never in the same cell as ours. This definition needs the user's review.

## 9. Not requirements

Temporal localisation, real-time operation, the best model in the world (D-005, D-011), and a claim about content kinds that the training and test data do not cover (O-002).

## 10. Open questions that still shape the requirements

O-002 (how each input is handled), O-006 to O-009 (MVP, backbones, fine-tuning, fusion), O-010 (rPPG test design), O-011 (software form).
