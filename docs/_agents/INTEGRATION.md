## Design choice for the preprocess id (D-028 item 4)

The contract is kept, not weakened: a checkpoint is scored only with preprocessing the code can apply exactly as trained. The checkpoint records `preprocess_config`; `load_checkpoint` requires (a) `preprocess_id` equals the hash of the recorded config (otherwise `PreprocessMismatchError`) and (b) the id is in `ACCEPTED[task]` (otherwise `PreprocessMismatchError`). For T-A, `ACCEPTED` holds the new trim-and-normalise id and the I-0 first-window id; the adapter reads `peak_normalise` from the recorded config and applies the matching path. So the I-0 checkpoint still loads and scores audio by its own first-window rule, a v2 checkpoint scores by the trimmed rule, and a checkpoint with any other audio configuration (another window, another sample rate) is refused. The alternative (refuse every checkpoint whose audio id is not `IN_USE`) would make the I-0 checkpoint unusable for T-V and T-I as well, because the check runs for all tasks at load.

If the owner prefers the strict reading (a v1 audio head is refused outright), remove the I-0 id from `ACCEPTED["T-A"]` in src/dfd/prep/config.py: one line, and the tests `test_a_version_1_audio_checkpoint_is_still_scored_with_the_first_window_it_was_trained_with` and `test_version_1_checkpoint_roundtrip_still_works` then have to be adjusted.

## Tests

`PYTHONPATH=src .venv/Scripts/python.exe -m pytest tests -q -x` with `CUDA_VISIBLE_DEVICES=` (result in the final report of the fork). The new tests cover: v2 load and scorer types; a video with a fine-tuned T-V and an ensemble T-A; the fine-tuned path equals a linear probe with the same head; temperature on the fine-tuned path; ensemble equals the sigmoid of the mean of the member logits; trim and normalise happen before the window; a v1 checkpoint with the I-0 audio id is scored with the first window; unknown audio preprocessing and an id that is not the hash of its config are refused; a missing weights file, a changed weights file, a changed member head file, an unlisted file and a missing `files` map are refused; a non-null `fusion` is refused; unknown model kind, empty member list and wrong member head width are refused; the v1 round trip.

## Open points

1. The real fine-tuned T-V path (separate encoder instance, parameter copy by name, fp16 autocast, Linear head) is covered by tests only through test doubles. The parity script has to be run on the GPU once; I expect agreement within 0.02 but have not measured it.
2. `encoder.dim` of the T-A ensemble block is the feature width of the first member (1536); the members carry their own widths and the loader checks each head against its own member width.
3. The fine-tuned weights file is loaded with `torch.load` (default `weights_only`), which accepts the dict of tensors, strings and numbers written by dfd.train.finetune.
4. scripts/mvp/train_mvp.py (the I-0 build) now writes the new audio configuration if it is run again, because `audio_config()` defaults to the trimmed rule. It was not edited; do not rerun it to rebuild I-0.
5. The audio-visual fusion mode is not implemented. What is needed (after E-011): the LAV-DF unimodal heads in the same checkpoint format (a `finetuned_encoder` visual model for `modify_video`, an `ensemble_logit_mean` audio model for `modify_audio`, each with its own temperature fitted on the fusion-fit subset), and a fusion block with the 3 logistic-regression parameters (intercept, visual weight, audio weight) on the calibrated log-odds. Then: (a) allow a `fusion` block of kind `logistic_regression` in `load_checkpoint` (it is refused today), (b) implement `RealAdapter` fusion of the visual and audio scores of a video and return a fused score with the decision threshold, replacing `AUDIO_VISUAL_FUSION = None` and the "undetermined" decision in dfd.infer.library for videos with both scores (O-009 and D-027 need a decision there), (c) decide whether the FF++ and ASVspoof heads or the LAV-DF heads serve the audio-visual mode, and show that choice in the response model block.
