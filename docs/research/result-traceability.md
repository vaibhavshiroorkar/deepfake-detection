# Result traceability

## Traceability contract

Every reported number must resolve to an analysis command, content hashes, and
MLflow runs. The registry stores references. MLflow stores parameters, metrics,
runtime details, and artifacts.

## Result registry

Regenerated by `scripts/update_result_registry.py`, which declares each row next
to the command that produces it and computes the hashes from the files. Do not
edit the table by hand: a hash typed in stays put while the artifact moves, and
a stale hash still reads as evidence.

Hashes are the first 16 hex characters of the file's SHA-256. `missing` means
the artifact is not in the checkout, and that row is `pending` whatever else
resolves.

## Acceptance rules

A result becomes `accepted` only when every hash resolves, every required seed
is present, and the analysis uses the frozen protocol. Failed and superseded
runs remain in MLflow. Smoke fixtures cannot enter this registry.

Three statuses are in use.

`accepted` meets every rule above. `provisional (1 seed)` has hashes that all
resolve and an analysis that follows the protocol, but was trained on one seed
where [the research design](../research-design.md) asks for three. Every Design
B result is currently in this state, and the paper reports it as a limitation
rather than rounding it up. `pending` has an artifact that is not in the
checkout; the row names the command that would produce it.

MLflow runs for the Design B streams were written by
`scripts/backfill_mlflow.py` from the history files the trainer left behind,
because Design B was trained through direct CLI calls and tracking is wired to
`ddf run --config`. Those runs carry `backfilled=true` and the SHA-256 of the
file they were built from, so a backfilled run is never mistaken for a live
one.
